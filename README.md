# sport workspace

В этой папке два независимых репозитория:

- `frontend/` - Expo приложение
- `backend/` - Go сервисы + `docker-compose.yml`

Цель - удобный локальный запуск без объединения git-историй.

## Требования

- Docker + Docker Compose v2
- Node.js + npm

## Быстрый старт (локально)

0) Проверка окружения

```bash
make doctor
```

Если нужен `backend/.env` (JWT/ключи), можно сгенерировать его из примера:

```bash
make backend-env
```

1) Инфраструктура для backend (db/mongo/kafka)

```bash
make infra-up
```

2) Backend сервисы

```bash
make backend-up
```

3) Frontend (в отдельном терминале)

```bash
make frontend-install
make frontend-start
```

## Полезное

```bash
make logs
make backend-down
```

## Переменные окружения

- Скопируй `backend/env.example` в `backend/.env` и поменяй значения при необходимости.

## Проверки исправлений

### Регистрация и выход

Регистрация сохраняет уникальность никнеймов. `auth` синхронно подтверждает
создание профиля через `USER_PROFILES_ADDR` и только затем активирует аккаунт
и выдаёт токены. Занятое имя возвращает `USERNAME_ALREADY_EXISTS`; отклонённая
попытка не занимает email. При неопределённом результате сетевого запроса
сохраняется незавершённая регистрация: вход запрещён, повтор с теми же email,
никнеймом и паролем продолжает её с прежним ID.

Событие регистрации записывается в PostgreSQL вместе с активацией и первым
refresh-токеном. Фоновый обработчик повторяет доставку в Kafka. Повтор события
не перезаписывает уже изменённый профиль. Существующие аккаунты и отсутствующие
профили не восстанавливаются автоматически.

После обновления кода пересоберите оба сервиса из корня репозитория:

```bash
docker compose -p sportapp-local up -d --build --no-deps user-profiles auth
```

В профиле справа вверху кнопка выхода теперь имеет подпись «Выйти» и область
нажатия не меньше 44×44. Frontend обновляется обычной web-сборкой.

### Тесты

Для тестов frontend используйте Node.js 22.12+, 24 или 26 и npm.

```bash
cd frontend
npm ci
npm run typecheck
npm run lint
npm test
npx playwright install chromium
npm run test:e2e
```

`test:e2e` собирает production web-версию и проверяет её в браузере. API в этих
тестах подменён локальными ответами; пользовательские данные не изменяются.
Для уже запущенной web-версии можно задать `E2E_BASE_URL` и выполнить
`npx playwright test`.

В каждой папке backend с `go.mod` выполните `go test ./...`.
Интеграционные тесты регистрации находятся в `backend/services/auth/integration`.
Для их запуска задайте `AUTH_TEST_DB_DSN` и `PROFILES_TEST_DB_DSN` (PostgreSQL URL),
а также `PROFILES_TEST_BINARY` — абсолютный путь к исполняемому файлу, собранному
командой `go build -o <путь> ./cmd` в `backend/services/user-profiles`.
Затем выполните `go test -v ./...` в `backend/services/auth`. Тесты создают
изолированные временные схемы в двух БД и удаляют их после завершения;
пользовательские таблицы и Kafka-проекции не изменяются.
SQL-регрессии запускаются отдельно в PostgreSQL/WASM без Docker:

```bash
cd backend/tests/sql
npm ci
npm test
```

Сервис activities автоматически применяет совместимую миграцию
`backend/migrations/activities/002_activity_requests.sql` при старте. Она добавляет
ключи повторных запросов и версии списков пользователя. Обновляйте frontend и
backend вместе. Уже существующие дубликаты не удаляются автоматически.

Для аватаров gateway проксирует `/avatars/` в user-profiles. Новые записи хранят
относительный путь; приложение разрешает его через `EXPO_PUBLIC_API_URL`.

## Дата, участники и места

На главной «Мои активности» по умолчанию показывает все записи пользователя,
включая прошедшие и участие в чужих активностях. Список отображается страницами
по 10 записей с кнопками «Предыдущая»/«Следующая». Это клиентская пагинация
полного списка из `/views/home`; необязательный фильтр применяется перед
разбиением на страницы. Переключение фильтра возвращает на первую страницу.
Карточки явно различают «Вы организатор» и «Вы участник».

Кнопка редактирования доступна, когда `organizerId` активности совпадает с ID
текущего пользователя из `sub` токена сессии. Это только условие отображения:
сервер проверяет подпись токена и принадлежность активности перед обновлением.
Загрузка активности не зависит от сервиса профилей: если имя или аватар
недоступны, остаётся нейтральная подпись, а просмотр и действия продолжают работать.
Редактор отправляет только изменённые поля, поэтому
изменить название прошедшей активности можно без повторной отправки её старой
даты. Если меняется сама дата, новое значение должно быть в будущем.

Список из 10 видов спорта общий для главной страницы, профиля, фильтров и
мастера создания. Календарь позволяет выбирать дату за пределами ближайшей
недели, время — с точностью до минуты. Те же поля используются при редактировании.

`maxParticipants: 0` означает отсутствие лимита. В этом режиме `spotsLeft: 0`
не означает заполненную активность: активность остаётся `OPEN`. Конечный лимит
от 2 до 1000 включает организатора. Вступление, выход и изменение лимита
атомарно обновляют участников, свободные места и статус. Нельзя уменьшить лимит
ниже текущего числа участников.

`POST /places/list` принимает `{search?: string, placeId?: string}` и возвращает
`{items: [{placeId, address, lat, lon, sports}]}`. Список формируется из адресов
существующих активностей, включая прошедшие; одинаковые адреса и координаты
объединяются. Поиск возвращает до 200 мест. Удаление всех исходных активностей
удаляет и адрес из этого списка. Это повторное использование мест, а не отдельный
сервис бронирования площадок. Пять исходных примеров площадок отмечены отдельно.
Ручной ввод адреса не выполняет геокодирование; известные координаты копируются
при выборе сохранённого места.

Миграция `backend/migrations/activities/003_capacity_and_reports.sql` применяется
автоматически при запуске activities. Она разрешает отсутствие лимита,
пересчитывает старые счётчики мест по участникам и позволяет текстовые жалобы
длиной 1–2000 символов. Повторная жалоба пользователя обновляет его запись.
ID заявителя берётся из авторизованного запроса. Миграция не удаляет активности.

После обновления исходников пересоберите три изменённых сервиса из корня репозитория:

```powershell
docker compose -p sportapp-local up -d --build --no-deps activities views map-activities
```

Для локальной web-версии выполните `npm run build:web` в `frontend`, затем
обновите вкладку. Команда `node scripts/serve-web.mjs` запускает сервер экспорта на 4173.

Дополнительные интеграционные тесты используют отдельную случайную PostgreSQL
схему и MongoDB базу, которые удаляются после теста. Переменные должны указывать
на локальные тестовые серверы с правами создания схемы/базы:

```powershell
$env:SPORTAPP_TEST_DSN='postgres://postgres:postgres@localhost:5433/activities_db?sslmode=disable'
go -C backend/services/activities test ./... -count=1
$env:SPORTAPP_TEST_MONGO_URI='mongodb://localhost:27017'
go -C backend/services/map-activities test ./... -count=1
```

Без этих переменных интеграционные сценарии пропускаются. Они проверяют
конкурентное вступление, повторные запросы, смену лимита, миграции, текстовые
жалобы, повторное использование мест и устойчивость Mongo-проекций к старым,
повторным и пришедшим после удаления событиям.
